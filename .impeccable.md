# Licensio Knowledge Base — Design Context

## Design Context

### Users
The same people who run License Server: small agencies and independent vendors selling WordPress plugins and themes. In the admin they are *authors and triagers* — writing documentation, reading what readers found unhelpful, adjusting how the knowledge base presents itself. On the front end the audience is different and larger: their customers, arriving from a support ticket or a search, usually mid-problem and impatient.

Two audiences, two moods. The admin is unhurried and deliberate. The front end is someone stuck at 11pm.

### Brand Personality
**Reliable. Clear. Calm.** — deliberately identical to License Server, because to a customer these are one product.

Emotional goal in the admin: *in control*. Nothing surprising, nothing that needs learning twice. Emotional goal on the front end: *found it*. The answer, quickly, with no ceremony in the way.

### Aesthetic Direction
**Reference**: Stripe Dashboard, Linear, Clerk. Refined light-mode tooling, strong typographic hierarchy, purposeful whitespace, restraint.

**Theme**: Light mode only. No glassmorphism. No gradients on text in the admin.

**Colour**: `#40b58a` is the brand and is **decorative only** — it measures 2.56:1 on white, below the 3:1 WCAG requires of a UI component, and white text on it is 2.56:1 against a 4.5:1 requirement. Anything that carries meaning or takes a click uses `--lkb-accent` `#247a5c` (5.23:1). The front end keeps `#2ba377`, the theme's `--primary`. Admin chrome and published pages are different surfaces; the settings screen renders the front-end colour as a swatch, and a swatch is content.

**Typography**: System stack in the admin — it should blend with the host, not announce itself. The front end uses the theme's Plus Jakarta Sans / Inter via `var(--font-head)` / `var(--font-body)` with real fallbacks, and never enqueues a font of its own.

**Logo**: `assets/images/logo/knowledge_base_icon.svg`. Same weight and green as License Server's icon, different silhouette — two adjacent menu entries sharing a shape are unnavigable once the admin rail collapses and the label disappears. Use it in the menu and in empty states; **not** as a persistent header on every screen, where it only repeats what WordPress already displays.

**Anti-references**: dashboards that open with a row of identical stat cards; anything that puts a large rounded icon above every heading.

### Design Principles
1. **Composure over flair** — if an element does not help the reader find or judge an answer, remove it.
2. **Hierarchy through restraint** — one primary action per screen.
3. **Token consistency** — colour, spacing and radius come from `apps/styles/tokens.css`. A hex literal in a component is technical debt.
4. **Light and data-dense, not sparse** — this is a tool. Moderate density is correct.
5. **Ink over chrome** — content is the interface. Borders, shadows and backgrounds only where they separate or elevate something.
6. **One word per thing** — an *article* is the item, the *knowledge base* is what is administered, *Documentation* is the published section. Three nouns for three objects is register; the same object under four names is a bug.

### Naming
| Object | Word | Where |
|---|---|---|
| A single piece of content | Article | CPT label, editor |
| The thing being administered | Knowledge Base | admin menu, plugin name |
| The published section | Documentation | archive heading, site nav (Docs), `/docs/` |
